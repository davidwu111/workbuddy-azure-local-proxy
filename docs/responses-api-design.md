# Azure Responses API bridge design

**Status: Steps 1–3 implemented and verified offline; Step 5 Chat mapping review and diagnostics are implemented and offline-tested pending Lead full-suite verification; native creation remains default-off, and specialized feature expansion and live checks are pending.** This document records the approved architecture and staged boundaries. Current behavior is documented in the [native create API](<native-responses-api.md>) and [native transport contract](<native-sse-contract.md>). The historical baseline appears below. The machine-readable event matrix is [event-inventory.json](<../test-fixtures/azure-responses/event-inventory.json>). This is not evidence of live Azure feature support or permission to make paid calls.

## Scope and non-goals

The optional native `POST /v1/responses` accepts the initial supported Responses-format JSON subset and returns native JSON or Responses SSE when explicitly enabled. The existing `POST /v1/chat/completions` request/response contract and mapping semantics remain unchanged. The two protocols may share trusted transport/security primitives, but the native route must not inject Chat chunks or an OpenAI Chat `[DONE]` sentinel.

Initial native scope is **create plus event transport only**. Retrieval, delete, background cancellation, response chaining, file management, and UI/client work are separate ownership-scoped extensions. Until the relevant gates exist, reject background mode, storage, chaining, agent references, and other privileged features conservatively. `store:false` is the default; true requires explicit storage consent. This proposal does not claim storage-off means inference remains local, zero retention, or no prompt caching.

This is protocol-preserving, not an arbitrary byte-for-byte proxy. Routing and policy may change known request fields only when explicitly specified; never use global string replacement. Valid unknown future native events may pass through under bounded framing with sanitized diagnostics. Malformed/conflicting known event/type or identity data, and truncated streams or missing terminal outcomes, fail visibly.

## Dual-protocol architecture

```text
Chat client ── POST /v1/chat/completions ── Chat validation/adapter ─┐
                                                                    ├─ shared auth, approved origin,
Native client ─ POST /v1/responses ─────── native validation ───────┘  alias routing, bounded transport
                                                                         │
                                                           configured Azure Responses create
```

- **Chat route:** existing Chat contract → existing Chat-to-Responses adapter → Chat JSON/SSE response. No semantic changes are part of this proposal.
- **Native route:** Responses request validation and policy → same approved origin and configured model-alias/deployment routing controls → Azure Responses create → native JSON or event-preserving SSE. Keep model alias selection separate from deployment identity.
- **Shared controls:** authentication; explicit approved Azure origins and redirect rejection; configured alias-to-deployment/profile routing; bounded request/response bytes, event frames, queues and concurrency; upload, header/read-idle, downstream-stall, total-lifetime and shutdown timeouts; disconnect cancellation and cleanup; privacy-safe diagnostics. Shared implementation must not accidentally impose Chat formatting on native output.
- The existing `parseSse` discards SSE `id`, `retry`, and comments, while `SseWriter` finishes with Chat `[DONE]`. They must not be blindly reused for native forwarding or modified in ways that alter Chat behavior. Build a native SSE path or a reusable transport layer with explicit Chat/native framing contracts.

## Request and response contracts

### Request

- Require authenticated `POST /v1/responses`, `Content-Type: application/json`, bounded UTF-8 JSON body, and only explicitly supported Responses fields.
- Resolve the caller's permitted model alias through configured deployment/profile routing. Do not accept an arbitrary deployment or origin from the request; do not infer deployment capability from an alias or from Azure's schema.
- Validate each option against a **pre-existing** model/feature/resource/tool/connection permission profile. Unknown/unsupported/privileged fields are rejected before upstream POST, not silently dropped or deferred until a later phase. Profile additions require explicit approval and verification.
- Default `store:false`. Require explicit consent plus a storage permission for `store:true`. Until implemented permissions exist, reject `background`, `previous_response_id`/chaining, agent references, and other privileged state features.
- Native JSON returns the Azure Responses object in Responses shape, retaining complete output items, content blocks, annotations, usage, item/response IDs, and opaque state. Preserve native `model` values as Azure returns them: aliases select an input route, not a replacement for provider output identity. The existing Chat route continues returning its configured alias.
- Validate native response structure without calling the Chat-only response extractor. A provider `failed` or `incomplete` outcome remains provider data, not a forged successful Chat completion. Do not flatten raw reasoning into a summary or log content.

### Streaming response

- Successful stream is `Content-Type: text/event-stream; charset=utf-8`, in source order, with native `event`, `id`, `retry`, and `data` fields preserved (including `sequence_number`, item IDs, output/content indices and annotation payloads). Never fabricate an Azure sequence number or response identity, or synthesize Chat chunks or `[DONE]`.
- **Comments/heartbeats:** preserve valid upstream comment and metadata-only records in order, under the same line/event/aggregate byte limits. They refresh upstream activity but are not semantic output or terminal events. Preserve explicit empty IDs and valid decimal retry values according to SSE rules; reject control-character/framing injection rather than interpolate unchecked field values.
- Unknown future native events require bounded UTF-8 framing and a valid typed JSON object, with event/type conflict checks. Forward their data without lossy interpretation; log only a bounded sanitized event name. Never guess that an unknown event is a successful terminal outcome.
- Preserve complete known terminal/error frames and output items. Validate lifecycle status and response identity when present; sequence numbers are ordered, not necessarily contiguous. Validate item identity only against actually observed item lifecycles and their documented identifiers. Do not require an output index to be the same identity as a tool call ID or impose invented universal ordering across parallel items.
- Partial native function/custom-tool arguments intentionally reach the caller before completion. They are data, not authorization to execute: the client must wait for a complete permitted call and apply its approval policy. Existing Chat terminal-buffered tool timing stays unchanged.
- Azure `error` events may have flat or nested error details; preserve either native form. Forward a validated known terminal/error event and finish without a Chat sentinel. Truncated EOF, missing terminal outcome, malformed known payload, or conflicting event/type/identity remains a visible failure, never normal success.
- Before streaming headers, local failures return bounded JSON errors with an appropriate HTTP status. After headers, local failure must be unmistakable and bounded, using a bridge-origin error notification whose exact schema is frozen with the Step 2 tests, then closing the stream; if delivery is stalled or disconnected, destroy the connection. Do not fabricate an Azure terminal response or upstream identity/sequence for that notification.
- Preserve upstream HTTP error status where valid and allowlisted safe headers. Redact configured credentials/origin from error messages and diagnostics only, without globally rewriting native payloads or opaque state. No automatic generation retry, including after any emitted bytes.

This review extracted the enum block on **2026-10-22** from the complete public page response in memory. It contains **53 unique event names**; repeated schema examples elsewhere on the page are not additional enum members. Baseline repository revision: `ce1a3a3`.

### Current Chat classification

The [current `sse.js`](<../sse.js>) has 13 mapped/handled documented enum event names, 8 explicit no-op enum names, 2 deliberately suppressed raw-reasoning names, and 1 lifecycle notification name (`response.queued`); the remaining 29 documented enum names are absent from its dispatch branches and rejected as unsupported by the Chat path. The 11 explicitly non-content acceptances are the 8 no-ops, both `response.reasoning_text.*` names and `response.queued`; queued is a lifecycle notification, not a no-op. `response.queued` requires an object `payload.response`, captures response id/`created_at` for identity exactly as `response.created` does, but emits no role chunk and is not terminal; `response.created` and `response.in_progress` are unchanged. `response.reasoning_text.delta/done` validate their `delta`/`text` string and are then discarded: raw reasoning never becomes Chat content or `reasoning_content`, is never retained and is never logged, while malformed payloads still fail. Unknown/unsupported names still throw `unsupported_sse_event` (no blanket catch-all), and a named Chat stream failure may attach only a bounded sanitized `eventName` to the request log—never payload, text, reasoning, tool data or provider messages. The Chat adapter's additional `response.cancelled` name is a separate compatibility terminal branch, not an enum member. There are **29 documented names absent from current Chat behavior**: audio (4), code interpreter (5), file search (3), web search (3), image generation (4), MCP (8), and custom tools (2). The inventory explicitly distinguishes Chat `mapped`, `noop`, `suppressed`, `lifecycle`, and `rejected` policies and also carries the extra `cancelled` name separately. Counts reconcile as **13 + 8 + 2 + 1 + 29 = 53**.

### Native proposed policy by class

| Event class | Events | Proposed treatment |
|---|---|---|
| Lifecycle and terminal | `response.queued`, `.created`, `.in_progress`, `.completed`, `.failed`, `.incomplete`, plus `error` | Validate known lifecycle/terminal structure, response ID/status consistency, preserve frames and order. `cancelled` is not a documented enum event; handle a cancellation outcome only when the native protocol actually provides it, not by inventing an enum member. |
| Items, content, text, refusal, annotations | output item add/done; content part add/done; output text delta/done; refusal delta/done; text annotation added | Preserve full material events, identifiers, indices, annotations, and order; never treat a no-op in Chat as no-op natively. |
| Reasoning | summary part/text events and raw `response.reasoning_text.delta/done` | Preserve opaque valid event data for the native caller only under configured privacy policy; never flatten raw reasoning into a Chat summary or expose it in logs. Do not manufacture summaries. |
| Function calls | function argument delta/done and output-item lifecycle | Preserve complete native call events and IDs. Bridge does not execute them. The authorized client/tool runner applies its approval policy. |
| Audio, code interpreter, file search, web search, image generation, MCP, custom tools | 29 events | Preserve only when the corresponding feature and resource/connection/tool permission was approved and enabled before route activation. Otherwise reject request before inference or fail closed if unrequested provider events arrive. No event enum entry proves that a deployment supports the feature. |
| Future valid unknown event | Not in enum | Bounded framing and sanitized diagnostic, then forward event/data without interpreting its payload; malformed framing or conflicts fail visibly. |

Do not count `response.deleted`, OpenAI-only names, or the distinct Azure AgentServer SDK enum. ## Security, permissions, tools, storage, ownership

- **Permissions are prerequisites to enable the native route**, not a later feature step: establish model/deployment, modality/feature, resource, hosted-tool/custom-tool, and connection permissions and explicit approved profiles before the create endpoint can forward requests. Default deny privileged or unverified features.
- Use only authenticated caller identity and configured model aliases; never let request content select Azure origin, deployment, arbitrary tool connection, or another owner's response/state. Shared origin allowlists and redirect rejection remain mandatory.
- Client executes function/custom calls only after explicit user/application approval. Azure executes only hosted tools expressly enabled in an approved route profile. Preserve requested approvals and policy decisions; never auto-approve, auto-execute, or run generated tools merely because an event appears.
- Bound body bytes, frame/line/event bytes, aggregate response bytes, in-memory queues, concurrency and wait queues; enforce idle, total, downstream-stall and shutdown deadlines. Propagate client cancellation upstream; dispose readers and release slots on every exit path.
- Keep logs privacy-safe: allowlisted event names, route alias/profile identifiers, bounded status/code and counters only. Never log prompts, response payloads, tool arguments/results, raw or summarized reasoning, opaque state, credentials, sensitive IDs, or connection secrets. Redact upstream messages/headers before returning or recording. Do not log unknown-event data.
- Keep all state and any future retrieval/delete/cancellation/chaining explicitly owner/auth-scope/deployment scoped. This create-only design introduces no sidecar, conversation store, response retrieval, delete operation or background task manager.

## Proposed module responsibilities

These names are design roles, not files or implementation claims:

1. **Native request validator/router:** enforce request field contract, auth context, alias/profile resolution, permissions and conservative privileged-feature rejection before network activity.
2. **Shared Azure transport:** apply approved origin, authentication material from existing configuration, method/path, redirect/error handling, bounded request/response, safe headers, timeouts, cancellation and no-retry behavior while preserving protocol separation.
3. **Native SSE frame reader/writer:** preserve ordered `event`, `id`, `retry`, `data` and documented comments/heartbeat behavior; validate UTF-8, framing, byte limits, type conflicts, known event structure and terminal outcome; generic bounded future-event passthrough.
4. **Native response serializer:** return JSON/stream responses without Chat translation, retaining complete output/annotation/usage/item identity and opaque state.
5. **Safe diagnostics:** emit only allowlisted, sanitized metadata and no event payloads or reasoning.
6. **Permission/profile registry:** define pre-enabled model, modality, resource, tool and connection gates; no implicit capability discovery or permissive defaults.

## Six sequential implementation and verification gates

All gates are sequential. Offline work should use synthetic fixtures and loopback mocks only. **The minimum safety gates listed below must be satisfied before Step 3 (route activation/endpoint can send inference):** shared authentication/origin/routing, bounded bytes/queues/concurrency/timeouts/cancellation/shutdown, privacy-safe logs, default-deny model/feature/resource/tool/connection permissions, storage consent with `store:false` default, tool execution/approval boundary, no automatic retries, and visible malformed/truncated/terminal errors. If any prerequisite is absent, Step 3 may be developed behind an unreachable/disabled path but must not forward a request.

1. **Coverage plus Chat baseline.** Freeze and review the 53-name inventory against the Azure enum and event schemas; lock down current Chat's 13 handled + 8 no-op names, 32 absent names (including category breakdown), and separate `response.cancelled` compatibility. Record existing Chat HTTP/JSON/SSE behavior. Acceptance: inventory has 53 unique enum rows and category/mapping counts reconcile; synthetic baseline checks show no Chat contract change. No production edits in this design stage.
2. **Shared native event layer.** Implement independent bounded native SSE framing/validation with preservation of `event`, `id`, `retry`, `data`, ordering, comments/heartbeat policy, UTF-8 and sequence/item identity; generic bounded unknown-event forwarding; terminal/truncation/conflict failures. Acceptance: synthetic fragmentation/newline/multiline/comment/metadata/unknown/identity/limit/cancellation cases pass, with no `parseSse`/`SseWriter` Chat semantic changes.
3. **Native create endpoint (safety-gated).** Add `POST /v1/responses` JSON and SSE create paths with shared auth/origin/routing, approved profiles, bounds/timeouts/cancellation, error policy, privacy-safe logs, `store:false` and no automatic retries. Acceptance: mock-only request/response contracts and cancellation/error paths pass; mandatory safety prerequisites demonstrably exist before route can forward. No live inference by default.
4. **Expanded feature gates.** Add separately approved model/profile gates for any additional modalities, hosted tools, custom tools, resources or connections. Keep background/storage/chaining/agent references and related privileged state rejected until their distinct implementations exist. Acceptance: each feature is denied by default, enabled only through explicit profile permission, and cannot be selected by client-controlled origin/deployment/tool credentials. Azure image-generation streaming caveat remains a deny until live verification is separately approved.
5. **Chat mapping review plus diagnostics.** Independently review existing Chat mappings and no-op policies against current documented enum changes; do not change them as collateral native work. Add sanitized unknown-event / protocol-failure diagnostics without payload leakage. Acceptance: compatibility diff and regression review show Chat behavior unchanged unless a separately reviewed, approved change is made; adversarial log tests contain no prompts, tools, reasoning or opaque state.
6. **Comprehensive synthetic tests plus separately approved live checks.** Run full mock/offline coverage for nonstream and streaming JSON, all known event classes, event metadata/order, future unknown events, malformed/conflicting/truncated frames, byte/queue/concurrency limits, timeouts, disconnect/shutdown, tool permissions and no retry; lead/maintainer executes baseline suite separately. Any Azure/client check needs a distinct approval naming exact resource origin, deployment/version/region, model/features/tools, sanitized input, call count/output cap, budget/stop condition, client version, evidence handling and deletion. Acceptance: synthetic results recorded without overclaim; live matrix remains not run until approval, and never executes generated tools automatically.
