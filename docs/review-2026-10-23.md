# Code review — GPT-6 native Responses update (`adapter-v2.11-native-create`)

Review date: 2026-10-23
Reviewer: WorkBuddy (independent static + dynamic review)
Baseline: working tree at `ce1a3a3` plus **uncommitted** changes (10 modified, 14 untracked files)
Scope: 12 runtime modules (~2.9k LOC), 13 test files (~3.5k LOC), 10 documents, launcher and CI config

---

## 1. Verdict

The implementation quality is high: the code is defensive, the failure modes are explicit, the
privacy boundary is consistently enforced, and the offline suite passes (343 tests, 339 passed,
4 Linux-only skips, 0 failed on Node 24.14.0).

The problems are **not** in the core conversion logic. They are concentrated in four areas:

1. **Delivery state** — the entire update is uncommitted, so there is no reviewable diff, no
   rollback point, and no CI signal for the change set.
2. **Documentation surface** — the main README does not mention the new `/v1/responses` route at
   all, and its evidence numbers and build identifier are stale. For a project whose stated value
   is evidentiary discipline, this is the most damaging class of defect.
3. **Scope claim** — the update does not "support all Azure GPT-6 API features". It supports a
   carefully gated subset. The gap is documented in sub-documents but not at the entry point, and
   several *inert default* values are rejected, which breaks SDK clients that serialize defaults.
4. **Interop edges in the native path** — nullable/empty-default handling, one dead validation
   branch, and a strict error-event shape that can mask real provider errors.

No credential leakage, authentication bypass, SSRF path, or unbounded-memory path was found.

## 3. Detailed findings

### R-01 (S1) — The entire update is uncommitted

`git status` shows 14 untracked files, including every native module
(`native-request.js`, `native-sse.js`, `native-events.js`, `native-permissions.js`), all native
tests, `live-check.cjs`, and five documents. Ten tracked files are modified but uncommitted.

Impact:

- No reviewable diff, no rollback point, no CI run for this change set.
- The launcher and `/healthz` identity checks compare `build` + `configId`; an operator restarting
  from this tree gets `adapter-v2.11-native-create` from code that exists nowhere in history.
- Any disk loss destroys the feature.

Fix: commit in logical units before further review — (1) native runtime + tests, (2) documentation,
(3) launcher/live-check tooling. Tag the commit so the review baseline is unambiguous.

### R-02 (S1) — The new route is invisible in the main README

`README.md:76-82` lists four endpoints. `POST /v1/responses` is absent, as is
`BRIDGE_NATIVE_RESPONSES`, `BRIDGE_NATIVE_POLICIES`, and every `docs/native-*.md` file. A repository
search for `BRIDGE_NATIVE` returns hits only in `.env.example` and the sub-documents.

Impact: an operator reading the entry document cannot learn that a second, privileged API surface
exists, that it is default-off, that it is deny-by-default per feature, or that enabling it requires
per-alias grants. `docs/native-responses-api.md` is accurate but unreachable from the README.

Fix: add a "Native Responses (opt-in)" section after the Chat endpoint table with:

- the route and its default-off flag;
- the three-part store consent and the per-alias feature grants;
- a one-line statement that caching, sampling, `include`, `background`, `service_tier`, `metadata`
  and chaining are **rejected**, not forwarded;
- links to the five native documents.

### R-04 (S2) — The feature claim exceeds the implementation

Native route (`native-request.js:9`) explicitly rejects:

`previous_response_id`, `conversation`, `agent_reference`, `agent_session_id`, `context_management`,
`prompt`, `include`, `metadata`, `temperature`, `top_p`, `prompt_cache_key`,
`prompt_cache_options`, `prompt_cache_retention`, `service_tier`, `max_tool_calls`,
`safety_identifier`, `user`, `stream_options`, `routing_config`, `user_security_context`,
`structured_inputs`, `moderation`, `truncation`, `top_logprobs`.

Chat route (`adapter.js:291`) rejects: `audio`, `frequency_penalty`, `function_call`, `functions`,
`logit_bias`, `logprobs`, `modalities`, `moderation`, `prediction`, `presence_penalty`,
`prompt_cache_retention`, `seed`, `service_tier`, `stop`, `top_logprobs`, `web_search_options`.
The Chat streaming path additionally rejects 29 of 53 documented event types
(`acceptance-matrix.test.js:531`).

The two most consequential gaps for GPT-6 specifically:

- **No cache controls on the native route.** `prompt_cache_key` and `prompt_cache_options` are
  first-class on Chat but rejected on native, so a native client cannot participate in prefix
  caching at all.
- **No sampling on the native route**, and no `service_tier` anywhere, so priority/flex billing and
  determinism (`seed`) are unavailable through the bridge.

Impact: if the acceptance criterion is literally "all GPT-6 features", the criterion fails. If the
criterion is "the documented subset", it passes. This must be decided before more features are
added, because the gating model (R-11) will otherwise be extended ad hoc.

Fix: replace the claim with an explicit capability matrix in the README:

| Capability | Chat | Native | Gate |
|---|---|---|---|
| text / tools / structured output | yes | yes | — |
| prompt caching | yes | no (R-04) | — |
| sampling | effort-gated | no | profile |
| hosted tools | no | grant | `nativePolicies.features` |
| storage | opt-in | opt-in | three-part consent |
| chaining / background / include | no | no | deferred |

Then schedule the highest-value native additions: `prompt_cache_key`/`prompt_cache_options`,
`include` (needed for `reasoning.encrypted_content` and logprobs), and `service_tier`.

### R-05 (S2) — Inert defaults are rejected, breaking SDK clients

The project's stated policy is that *exact disabled/unset defaults are normalized* and only
*enabled semantic controls* are rejected. That policy is only partially implemented. Verified on
both routes:

```
Chat:    service_tier: "auto"                     -> 400 unsupported_parameter
Chat:    logprobs: false, top_logprobs: 0         -> 400 invalid_parameter
Chat:    moderation: "auto"                       -> 400 unsupported_parameter
Native:  metadata: {}                             -> 400 unsupported_parameter
Native:  include: []                              -> 400 unsupported_parameter
Native:  truncation: "disabled"                   -> 400 unsupported_parameter
Native:  top_logprobs: 0                          -> 400 unsupported_parameter
Native:  temperature: 1                           -> 400 unsupported_parameter
Native:  service_tier: "auto"                     -> 400 unsupported_parameter
```

Every one of these values is the documented default. Official SDKs commonly serialize a full default
object, so a client that is semantically identical to a working request can fail.

Note the inconsistency inside the same code base: `logprobs: false` alone *is* normalized
(`chat-contract.js:85`), but pairing it with the equally inert `top_logprobs: 0` fails at
`adapter.js:279`.

Fix:

1. Extend `NULL_AS_UNSPECIFIED`/`normalizeChatDefaults` with the exact inert values:
   `service_tier: "auto"`, `moderation: "auto"`, `include: []`, `metadata: {}`,
   `truncation: "disabled"`, `top_logprobs: 0`, `temperature: 1`, `top_p: 1`.
2. For `top_logprobs`, treat `{logprobs:false, top_logprobs:0}` as one inert pair.
3. For native, drop the inert value instead of failing; keep rejecting every non-default value.
4. Add regression tests that assert the *forwarded payload* contains no corresponding field.

Do not extend this to semantic non-defaults (`stop`, `seed`, penalties, `logit_bias`): those must
stay rejected, as they are today.

### R-06 (S2) — `max_output_tokens` is always sent

`adapter.js:471` (`request.max_output_tokens = requestedCap`) and `native-request.js:338`
(`payload.max_output_tokens = body.max_output_tokens ?? cap`) send a value even when the client
omitted one. The default is `min(BRIDGE_MAX_OUTPUT_TOKENS, profile.maxOutputTokens)` = **128000**.

Three risks:

1. **Hard 400 on smaller deployments.** If the Azure deployment's real maximum is below the
   operator-declared cap, every request fails upstream, including requests that never asked for a
   budget.
2. **Cost and latency inflation.** The budget covers reasoning plus visible output; a 128k default
   invites long generations where the provider default would have been far smaller.
3. **Semantics.** For a "native passthrough" route, injecting a field the client did not send is a
   silent behavioural change, which is the one thing this project otherwise refuses to do.

The native document states this behaviour (`docs/native-responses-api.md:21`), but the README does
not, and the consequence above is not discussed.

Fix (choose one, document it):

- **A (recommended):** add `BRIDGE_OUTPUT_BUDGET_MODE=default|cap-only` (default `default` for
  compatibility, `cap-only` for strict passthrough). In `cap-only`, omit `max_output_tokens` when
  the client omitted it and still reject explicit values above the cap.
- **B:** lower the default to a conservative value (for example 32k) and require an explicit
  operator opt-in for 128k.

Add a test that a request without `max_completion_tokens`/`max_output_tokens` produces a payload
with the field absent in `cap-only` mode.

### R-07 (S3) — `messages[].name`

`adapter.js:334` validates `name` as a string, then `:335` omits `name` from `messageFields`, so the
key falls through to `RESERVED_MESSAGE_FIELDS` at `:342` and is rejected as `unsupported_parameter`.
Result:

```
{role:"user", content:"hi", name:"alice"}  -> unsupported_parameter
{role:"user", content:"hi", name:7}        -> invalid_parameter "must be a string"
```

The first branch is dead code: no string value can ever reach a successful path.

Fix: decide the contract. The Responses message item has no participant-name field, so rejection is
correct — but make it uniform: delete the type check, and return `unsupported_parameter` for every
`name` regardless of type (or map `name` into the `input_text` metadata if the provider supports it,
which is not documented). Add a one-line test for both shapes.

### R-08 (S3) — Native `parallel_tool_calls: null`

`native-request.js:337` allows `null`, and `:346` forwards it. Chat normalizes `null` away
(`chat-contract.js:67`). If Azure validates the field as boolean, a native client that sends `null`
(e.g. from a serialized default object) gets an upstream 400 that the bridge could have prevented.

Same pattern for `text: {}` and `reasoning: {}`, which are forwarded as empty objects rather than
omitted.

Fix: omit `parallel_tool_calls` when `null`; omit empty `text`/`reasoning` objects. Add tests
asserting the forwarded payload.

---

### R-09 (S3) — Native `input: []` accepted

`native-request.js:306` requires `input` to be present but does not require it to be non-empty after
validation. An empty array reaches Azure and fails there, producing an `upstream_error` with the
provider's message instead of a local `invalid_parameter`. This is the only place where the native
validator delegates an obviously invalid request upstream.

Fix: reject empty arrays and empty strings locally, mirroring `adapter.js:307`.

### R-10 (S3) — Chat policies silently do not apply to native

`BRIDGE_INSTRUCTION_POLICY` (`config.js:107`) and `BRIDGE_SAMPLING_POLICY` (`:108`) are read and
validated globally, but `validateNativeRequest` never consults them. A native request can mix
`system` and `developer` roles even when `reject-mixed` is configured, and sampling is a different
code path entirely.

Impact: an operator who sets a global policy reasonably expects it to hold for every route. Silence
here is a governance gap, not a crash.

Fix: either (a) apply `instructionPolicy` in `inputItems` for native messages, or (b) state in
`README.md` and `docs/native-responses-api.md` that these two policies are **Chat-only**, and add a
startup log line or `--check-config-json` field indicating which route each policy applies to.
(a) is cheap for `reject-mixed` and preserves the project's "no silent divergence" rule.

### R-11 (S3) — Two capability models for one capability

| Capability | Chat gate | Native gate |
|---|---|---|
| image input | `profile.images` (`config.js:52`) | `nativePolicies.features:["image-input"]` |
| file input | unsupported | `features:["file-input"]` |
| explicit cache breakpoints | `profile.cacheBreakpoints` | no native cache support |
| hosted tools | unsupported | `features` + resource allowlists |

Both default to deny, so this is safe. The risk is operational: enabling `images: true` for the Chat
route does nothing for native, and the reverse. Two switches for one concept invites a
misconfiguration where an operator believes a capability is closed when it is open (or vice versa).

Fix: derive the native `image-input`/`file-input` grants from the profile (with the native policy
able to *narrow*, never widen), or add an explicit startup warning when the two disagree for the same
alias. Document the relationship in `docs/native-feature-permissions.md`.

### R-12 (S3) — Flat `error` event shape is too strict

`native-events.js:40` declares flat error fields as `{type, sequence_number, code, message, param}`,
and `:91` requires **every** declared field to be present. Verified:

```
{type:"error", sequence_number:3, code:"busy", message:"m", param:null} -> ok
{type:"error", code:"busy", message:"m", param:null}                    -> invalid_native_shape
{type:"error", sequence_number:3, code:"busy", message:"m"}             -> invalid_native_shape
{type:"error", error:{...}}                                             -> ok
```

The nested form is deliberately tolerant of a missing outer sequence number (`:86-90`), so the code
already accepts that providers vary. If a flat provider error omits `param` (the common case for a
null parameter) or `sequence_number`, the bridge replaces the provider's error with a generic
`bridge.error` / `invalid_native_shape`, destroying the diagnosis an operator needs most.

Fix: make `param` and `sequence_number` optional in the flat form; require only `type`, `code`,
`message`. Preserve whatever fields are present and keep the existing redaction. Add a fixture for
the minimal flat error. This is a *tolerant* change: it cannot admit a malformed success path,
because the event is terminal and is still emitted as an error.

### R-13 (S3) — Policy byte budget does not cover message content

`createNativeResponsePolicy` charges bytes for function/custom calls (`:404`) and hosted items
(`:438`), but `itemAllowed` for `message` (`:448`) and `partAllowed` (`:380`) charge nothing.
Verified: forty 1 MB `message` items (40 MB) are accepted with the default 16 MiB budget.

This is not a memory-exhaustion defect — the reader enforces `responseBytes` (64 MiB) independently —
but the budget is named `maxBytes` and is documented as a bound. Two different things are being
called the same name.

Fix: either charge `Buffer.byteLength(text)` for `output_text` and the image payload length, or
rename the internal field to `maxIdentityBytes` and document that content is bounded only by
`responseBytes`. Add a test that pins the chosen semantics.

### R-14 (S3) — Three event inventories

The same 53-event list exists in three places:

1. `native-events.js:5-25` (`groups` → registry);
2. `sse.js:157,161` (`NOOP_EVENTS`, `SUPPRESSED_RAW_REASONING_EVENTS`);
3. `acceptance-matrix.test.js` (hand-maintained inventory with exact counts).

The tests do guard against drift (the matrix asserts 53 entries and drives each one), so this is not
a correctness bug today. It is a maintenance tax: adding one event requires three coordinated edits,
and the two sets in `sse.js` are keyed by name rather than derived from the registry category.

Fix: derive `NOOP_EVENTS` from `EVENT_REGISTRY` categories (`message-content-lifecycle`,
`output-text` `.done`, `reasoning-summary` `.done`, `annotation`, `refusal` `.done`) and derive the
acceptance inventory from the registry plus a small explicit policy map. The test then asserts
category coverage rather than a transcribed list.

### R-15 (S3) — Missing `nativeCode` on the HTTP-error path

`server.js:249` sets `nativeCode` from `error.failureCode ?? error.code` inside the catch block.
On the normal upstream-error path (`:191-195`) the code returns from inside the `try`, so
`nativeCode` stays `undefined` and the request log for a native 429/400 carries no `code` field,
unlike a Chat request in the same situation.

Fix: set `nativeCode = String(upstream.status)` (or the sanitized provider code) in that branch, and
add a log assertion to an existing native HTTP-error test.

### R-16 (S4) — No `package.json`

Intentional for a zero-dependency project, but it also means:

- no `engines: {node: ">=22"}` for editors/CI;
- no `scripts.test` / `scripts.check`, so the command surface lives only in README prose;
- no `type: "commonjs"` declaration (currently inferred).

Low risk; a five-line `package.json` without dependencies would not violate the design goal.

### R-17 (S4) — `requestTimeout` vs queue wait

`server.js:269` sets `server.requestTimeout = config.timeouts.uploadMs` (30 s default), while the
admission queue can wait `capacityWaitMs` (30 s) **before** the body is read. The probe with a
300 KB queued body did not reproduce a timeout — Node applies backpressure and the request timer is
compatible in practice — but the two budgets are conceptually coupled and can collide for slow
uploads: queue wait + upload can exceed `requestTimeout` even though each stage is individually
within its own limit.

Fix: set `requestTimeout` to `capacityWaitMs + uploadMs` (clamped), or to `0` and rely on the
existing stage timers, which are already precise.

### R-18 (S4) — Dead exports and branch

`CLIENT_METADATA_MODES` (`chat-contract.js:49`) and `REGISTRY_VERSION` (`native-events.js:4`) are
exported and referenced only by tests. The `name` branch in `adapter.js:334` is unreachable for
strings (R-07). No functional impact.

### R-19 (S4) — `retry-after` on 2xx

`safeHeaders` (`server.js:72-80`) runs before the status branch, so an upstream `retry-after` header
is copied onto a successful response. Harmless, but it can confuse client retry logic that keys on
the header's presence.

Fix: apply `SAFE_HEADERS` only for `upstream.status >= 400`.

---

### R-20 (S4) — Refusal duplication

`adapter.js:708-709` sets `content` to the refusal text when there is no ordinary text, in addition
to `message.refusal`. This is documented (`docs/compatibility.md:230`) and tested
(`acceptance-matrix.test.js:506-511`), so it is a deliberate choice. It remains a client-visible
risk: a client that renders `content` will display a refusal as normal assistant text.

Recommendation: keep the fallback (some clients ignore `refusal`), but add a `bridge_warnings`
entry (for example `refusal_content_fallback`) so the behaviour is observable, mirroring the
existing `suppressed_invalid_or_incomplete_tool_calls` warning.

## 4. Verified sound (do not change)

These were checked and are correct; they should survive the fix plan unchanged.

- **Credential handling.** Separate local bearer and Azure key, timing-safe comparison
  (`server.js:45-50`), key sent only as `api-key` to the approved origin, `redirect: "error"`,
  reject of 3xx and `redirected` responses (`:187`), secret scrubbing in headers, error envelopes
  and log records. No credential occurrence in the two local log files was found (checked by exact
  match, counts only).
- **Repository hygiene.** `.env`, `*.log`, `certs/` are ignored and `.env` has never been tracked;
  the only tracked PEMs are test fixtures.
- **Native authorization model.** Deny-by-default per feature, per resource ID, per MCP server and
  per tool name; forced `tool_choice` narrows; `tool_choice:"none"` blocks calls; undeclared calls
  are rejected before emission (`native-request.js:356-510`). This is the strongest part of the
  update.
- **Streaming correctness.** Terminal output is authoritative; streamed text/tool arguments are
  reconciled with `startsWith`; conflicts fail instead of duplicating; tool calls are withheld until
  a validated terminal (`sse.js:244-276`). UTF-16 accumulation preserves split surrogate pairs.
- **Bounded resources.** Every reader, parser, writer and tracker has an independent byte or count
  budget; empty-chunk progress is bounded; queues drop rather than grow (`logger.js:122`,
  `native-sse.js:70`).
- **Failure semantics.** Local validation, upstream HTTP failure and stream corruption are
  distinguishable by status, `code`, `finish_reason`, `outcome` and log `stage`; there are no
  automatic POST retries.
- **Privacy.** Logs are allowlisted and field-typed; prompts, tool arguments, reasoning and provider
  text never enter a record; diagnostics paths are token-wise validated and truncated.
